小脸蛋造型宪法（实测版）

色号那场官司，四个说法里没有一个是编的，只有两个是同一个颜色的两种写法。 但真正让它们一会一个样的不是色号，是眼睛——方向和宽度，两条，三家全翻过车。 这一页把三张截图逐像素量完，两件事一起定下来。

按下面所有实测数值画的。把手机上的形象页并排放过来，应该分不出来。

同一颗球，被量了四次，报出五套数。它们各自是什么：

出处报的值与实际身份
截图像素 #E94697 #885BF4 #000000 真值，但它是 Display P3 编码。 球内 86–90% 的像素就是这一个数，没有渐变。
Grok 报的 #FF309B #9159FE #000 真值，是同一个颜色的 sRGB / CSS 写法。 与截图值双向换算闭合在 ±2 以内。它没编。

3为什么会冒出四个说法

不是谁在编。是「量到的数」和「该写的数」本来就不是同一个。

你的 iPhone 屏幕是 Display P3 色域，比 sRGB 宽。截图存下来的是屏幕上那一帧的原始数值， 也就是 P3 编码值。而这三张 PNG 里 ICC 描述文件被剥掉了—— 任何取色器打开它，都只能默认按 sRGB 去读，于是读出一个偏灰偏暗的数。

所以拿取色器吸的人（Gemini、那份 Chat 版），吸到的都是 #E94697 这一档； 而报 #FF309B 的，报的是它在 sRGB 里的写法。两边都没错，错的是没人说清自己在哪个空间。

验算是双向闭合的：把 #E94697 当 P3 反推回 sRGB，得 #FD3099； 把 #FF309B 正推成 P3，得 #EB4699。 两个方向、两个色相、六个通道，全部落在 ±2 以内。这个吻合度不可能是巧合。

旁证：截图里「重置为默认」那行蓝字量出来是 #3C82F4。 如果这张图真是 sRGB，iOS 那个蓝的 R 通道该是 0，不该是 60。 R 被抬起来，正是 P3 数值被当成 sRGB 读的特征。

4所以到底写哪个

一句话：给机器看的写 sRGB，跟截图比对的用 P3。

场景用哪一档
写 HTML／CSS
写 SVG		 sRGB：#FF309B / #9159FE / #000000 浏览器会做色彩管理，在你屏幕上显示出来就是原版那个样。
贴给模型
当造型指令		 同上，写 sRGB。 模型产出的是代码，代码里的 hex 默认就是 sRGB。
拿截图
逐像素核对		 P3：#E94697 / #885BF4 / #000000 核对的是同一台手机的同一种编码，这时候才比这一档。

反过来写会怎样：如果在 CSS 里写 #E94697，浏览器按 sRGB 读它， 再映射到 P3 屏上会变成 #D75395——比原版明显更灰、更暗。 紫同理，#885BF4 会掉成 #815DEC。

这就是为什么那份 Chat 版把 #FF309B 划掉、改用截图值去绘制， 画出来的三只会比手机里那三只闷一档。它删掉的恰好是对的那个。

5真正让它们一会一个样的，不是色号

色号写死一行就完了。每次画飘的是这里，而且有两条，三家全翻过车。

两道缝是反斜杠 \：顶端偏左，底端偏右。 右边那道比左边窄三分之一，那是球面透视。

第一条：方向。端点像素直接读得出来——顶端 (765, 563)，底端 (794, 618)。 从上往下走 x 在增大，所以是反斜杠 \，不是斜杠。 三张截图、两种算法（主轴分析与端点连线），结论一致。

这一条最容易翻，因为它只差一个负号，而且画出来仍然是「两道斜缝」， 不盯着看不出错——但整张脸的神态是反的。 判据只有一句：顶端比底端靠左。拿这句去验，比记角度正负号可靠。

坑在 SVG 和 CSS 的 rotate()：y 轴向下， 正角度会把顶端甩向右。所以要画出 \， 得写 rotate(-26.2)，负号。

倾斜方向\ 顶端偏左
两缝倾角差0.3°
两缝长度比1.000
两缝观测宽度比0.665
反投影后宽度比0.995
端点 x 随 y同增

把两道缝按球面反投影还原，真实宽度是 0.208R 和 0.207R——差 0.5%，是同一个形状。 长度比 1.000，倾角差 0.3°。三张截图分别量，三次都一样。

所以原版是一颗球，球面上贴了两道一模一样的缝；画到平面上，靠边的那道自然被压窄。 模型不知道这件事，就把它当成两个平的胶囊画成一样宽——脸立刻就平了， 那种「它在看你」的微妙劲儿全掉光。你觉得哪里不对又说不出，多半是这一下。

还有一条所有版本都写错的：缝不是白色的。芯部量出来是 #FCFCFC， 和页面背景一模一样——它是挖空的洞，不是涂上去的白墨。 写死 fill:#fff，放到深色背景上就露馅了。

浅底：缝看着是白的

深底：缝跟着变深

同一段代码，只换了底色。缝没有颜色——它只是没被填上。
